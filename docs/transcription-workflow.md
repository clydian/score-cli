# 从 PDF 到可用 MusicXML 的转谱流程

目标是让用户在产品中拿到忠于原谱、能读能练的谱子。原 PDF 是音乐内容的依据；已有 XML、OMR 输出和播放器渲染都是待核对的材料。本文记录工作的大方向；具体 CLI 参数见 [编辑与校准](editing.md) 和 [结构编辑](structural-editing.md)。发现新失败模式时，修改对应阶段的判断标准，并在下一首以及早期成果上验证。

## 两轮推进，分别交付

第一轮解决覆盖：优先复用底稿，尽快交付完整曲目的可用版本，清楚记录省略的伴奏、歌词或其他限制。允许精细排版和表达稍后完善；反复路线、声部缺失、明显错误音区和明显无原谱依据的奏法应先处理。每首记录“本地候选、已检查、已发布”的实际状态。

第二轮解决忠实度：按原谱逐小节、逐声部复查音乐及全部记号，补全第一轮省略的内容。首轮全部覆盖后，从最早的作品重新开始，让后期发现的方法和工具缺陷回用于早期版本。声乐已精校、伴奏尚未完成时，应明确按范围交付。

## 工作闭环

| 阶段 | 核心工作 | 进入下一阶段的依据 |
| --- | --- | --- |
| 清点与定源 | 从完整后台范围清点谱目；绑定谱目、PDF 版本、原件哈希；建立源页、系统、印刷小节的对应关系。 | 每条谱目有可追溯原件；同名谱、不同版本、不同云盘不会混淆。 |
| 建立底稿 | 比较已有 XML 与原谱的编制、调性、结构及版本；选择复用、OMR 或重建；记录全部声部和伴奏范围。 | 每个原谱段落都有对应内容或明确的待补项，底稿来源与省略范围可查。 |
| 音乐校订 | 优先用 Score CLI 定位、编辑、比较；按原谱核音高、时值、休止、声部、歌词及记号。 | 所有小节和声部完成有范围的源谱核对；疑点保留位置与证据，修订可重放。 |
| 显示与播放 | 对完整候选逐系统看谱；用实际产品引擎核播放，再进入产品实测。 | 全曲显示可读；音高、起点、持续时值、声部与反复路线吻合；未实现的表达有明确说明。 |
| 发布与回读 | 将已核对的同一份文件关联到正确产品谱目；从成员入口重新打开。 | 云端实际文件哈希等于复核文件，PDF 绑定正确，成员端显示、播放和修正项验证通过。 |

## 音符之外的记号要单独复核

“从头看过谱”不足以说明所有类别都已检查。音乐校订分两种视角交叉进行：从原谱找 XML 是否遗漏，从 XML 找每个额外记号的原谱依据。

- 音高与节奏：同时核谱号、调号、临时变化、移调、八度、附点、连音、休止和跨声部时间；先算乐谱时间，再核声音。
- 结构与延续：单独列出反复、第一/第二结尾、跳转、连音与延音链，沿实际演奏路线检查起止和衔接。
- 歌词与表达：分别核对歌词音节、连字符和延长线，以及跳音、重音、换气、延长、力度、速度等记号的位置与作用。

低清细节、异常音程或复核意见不一致时，回到高分辨率原谱，按谱号与五线位置重新定标，并由另一位复核者独立确认后锁版。

二轮音高复核先暂时脱离底稿：在能清楚辨认五条线的原谱裁图上，逐谱表确定谱号与线位，独立记录音名、时值和声部，再与 XML 比较。尤其检查空心符头、相邻分部和钢琴缩谱；按底稿音名回看低清整页，容易把整段偏一个线位的错误继续当作正确。发现这类系统性误读时，应撤回受影响范围的旧验收，扩大源谱重读范围；XML 到 MIDI 一致不能替代这一步。

每个反复或跳转标记都需要原谱位置与明确路线。OMR 新增的奏法和表情逐类复核；数量异常、全曲贯穿或彼此矛盾时优先排查。原谱确实存在的记号应保留，不能用“全部删除某类元素”替代复核。合法记号即使音乐含义错误，也可能通过 XML 校验。

## 验证分层，结论限定范围

结构校验、XSD、渲染、播放和原谱核对回答不同问题，应分别记录结果。播放器成功加载不能证明音准和节奏；实际 MIDI 的音高、起点、延音持续时间和播放顺序才有相应证明力。渲染应覆盖全曲及所有声部，重点回看歌词、奏法、表情与结构记号，而非只看改过的几个小节。

复核必须绑定同一份候选文件。分工时明确各人的声部和检查类别，汇合后检查声部间对齐与全曲行为；合并后的文件再渲染、再播放，旧哈希下的结论只作为历史证据。保留“已检查范围、未检查范围、未解决问题”，不以检查次数或测试数量代替音乐结论。

分工汇合时，还要证明已确认的源谱结论真正进入最终文件。独立源台账之间有冲突，先回到原图裁决并撤回旧结论，再按最终候选逐项核对裁决结果；不得让早期底稿或旧台账覆盖后来的源谱确认。用源台账到最终 XML 的差异清单检查遗漏，不能只确认修改脚本执行过，或只比较 XML 与自身导出的 MIDI。源台账、差异报告和筛选摘要只负责定位；裁决前应查看最终文件的完整小节及上下文，不能把摘要未列出的事件当作遗漏。

播放还需区分音符正确与表达实现。文字速度、自由节拍、延长记号等若未被当前引擎执行，应记录实际行为；任何演奏解释都与原谱明确数值分开。只有实际听过才记录耳听通过。共享钢琴符头等多声部写法需要区分谱面事件与实际击键：保留所有源声部，再核对合成前 MIDI 和实际合成结果，不能仅靠音符数量相等判定播放正确。

速度要独立核对记谱单位、附点、每分钟拍数和实际生效时点。先换算成四分音符 BPM，再检查引擎导出的全曲 tempo 事件；同一位置的文字/节拍器与 sound 不应互相错误覆盖，小节内 offset 必须按当前 divisions 换算。以附点四分音符 56、二分音符 54 及小节中途变速作为跨作品回归案例，不能只读播放器顶部的速度数字。若引擎只能显示等价四分音符标记，明确区分源 XML 保留情况、显示限制与实际速度正确性。

视觉游标、当前拍事件与声音时钟也要分别核实。谱面横向距离并非等比例时间轴；平滑游标可能朝下一音符插值，经过小节线后的留白。不能仅凭游标越过小节线就认定音乐不同步；先核对引擎设计、下一音符位置及真实事件时序，再判断是否影响排练。调整默认行为前，同时评估停顿、跳动和维护成本。

## 工具改进跟随真实障碍

工具阻挡正确记谱或产生错误显示、播放时，先建立能复现该问题的例子，再修复、补回归、更新用法，并回到真实谱验证。保留原谱合法的部分声部与共享音符；确需接受工具警告时逐项写明依据、绑定输入和输出哈希，警告仍留在报告中。当前 CLI 不支持的操作可使用范围明确、保护未改音乐、可追溯的例外处理。

工具测试验证工具行为，源谱复核验证音乐内容。工具版本确定后记录提交与测试证据，再应用到后续作品；没有实际需要时无需修改代码。

## 发布后的反馈继续进入闭环

用户反馈先定位产品当前实际文件，再与原谱、复核候选对照。修复应回到成员端验证同一症状；可靠的局部修订可以先更新产品，继续清楚标注剩余范围。将失败原因转成流程判断标准，并检查其他作品是否受到同类问题影响。

本流程的一次具体教训：2026-10-17，《If Music》第一轮发布文件含 39 个假跳音、7 个第一结尾（ending）元素；7 个元素不等于 7 段结尾。结构及播放加载检查允许这些合法 XML 元素，按段落看音区与旋律也未覆盖它们。第二轮校订候选已修正相关记号，但等待钢琴整合、尚未更新产品，使错误继续暴露。由此加入“记号分类复核、从 XML 反查原谱、发布后复现修正项”的要求；第一轮快速覆盖同样执行这一最低检查。
