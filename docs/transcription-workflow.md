# 从 PDF 到可用 MusicXML 的转谱流程

目标是让用户在产品中拿到忠于原谱、能读能练的谱子。原 PDF 是音乐内容的依据；已有 XML、OMR 输出和播放器渲染都是待核对的材料。本文记录工作的大方向；具体 CLI 参数见 [编辑与校准](editing.md) 和 [结构编辑](structural-editing.md)。发现新失败模式时，修改对应阶段的判断标准，并在下一首以及早期成果上验证。

## 两轮推进，分别交付

第一轮解决覆盖：优先复用底稿，尽快交付完整曲目的可用版本，清楚记录省略的伴奏、歌词或其他限制。允许精细排版和表达稍后完善；反复路线、声部缺失、明显错误音区和明显无原谱依据的奏法应先处理。每首记录“本地候选、已检查、已发布”的实际状态。

第二轮解决忠实度：按原谱逐小节、逐声部复查音乐及全部记号，补全第一轮省略的内容。首轮全部覆盖后，从最早的作品重新开始，让后期发现的方法和工具缺陷回用于早期版本。声乐已精校、伴奏尚未完成时，应明确按范围交付。

## 工作闭环

| 阶段 | 核心工作 | 进入下一阶段的依据 |
| --- | --- | --- |
| 清点与定源 | 从完整后台范围清点谱目；绑定谱目、PDF 版本、原件哈希；建立源页、系统、印刷小节的对应关系。 | 每条谱目有可追溯原件；同名谱、不同版本、不同云盘不会混淆。 |
| 建立底稿 | 比较已有 XML 与原谱的编制、调性、结构及版本；选择复用、OMR 或重建；记录全部声部和伴奏范围。 | 每个原谱段落都有对应内容或明确的待补项，底稿来源与省略范围可查。 |
| 音乐校订 | 优先用 Score CLI 定位、编辑、比较；按原谱核音高、时值、休止、声部、歌词及记号。 | 所有小节和声部完成有范围的源谱核对；疑点保留位置与证据，修订可重放。 |
| 显示与播放 | 对完整候选逐系统看谱；用实际产品引擎核播放，再进入产品实测。 | 全曲显示可读；音高、起点、持续时值、声部与反复路线吻合；未实现的表达有明确说明。 |
| 发布与回读 | 将已核对的同一份文件关联到正确产品谱目；从成员入口重新打开。 | 云端实际文件哈希等于复核文件，PDF 绑定正确，成员端显示、播放和修正项验证通过。 |

已有 MusicXML 优先作为底稿：先查本地曲库和可合法取得的公开版本，再决定是否重建。以原 PDF 核对编制、调性、乐章顺序、弱起、反复和小节对应；同名与小节数相同只说明值得比较，不能证明版本一致。保留来源与文件哈希，列出能复用的范围及版本差异。当前候选已完成源谱修正时，旧曲库文件用于补漏和独立比较，不能因格式更整齐而覆盖已确认的修正。

## 音符之外的记号要单独复核

“从头看过谱”不足以说明所有类别都已检查。音乐校订分两种视角交叉进行：从原谱找 XML 是否遗漏，从 XML 找每个额外记号的原谱依据。

- 音高与节奏：同时核谱号、调号、临时变化、移调、八度、附点、连音、休止和跨声部时间；先算乐谱时间，再核声音。 临时升降号按其有效范围逐音展开，核对同小节后续同音级、同八度的继承与取消；不能只校正印有符号的那个音。
- 结构与延续：单独列出反复、第一/第二结尾、跳转、连音与延音链，沿实际演奏路线检查起止和衔接。
- 歌词与表达：分别核对歌词音节、连字符和延长线，以及跳音、重音、换气、延长、力度、速度等记号的位置与作用。

表情图形的自动提取只用于定位，不能作为完整清单。跨行、跨页的渐强渐弱可能由分离的线段组成；按完整系统追踪起止与声部范围，区分一条延续线和两个独立指令。线尖落在持续音中时，记录可见位置与用于编码的编辑性时间锚，不把版面距离换算成原谱明确节拍。

建立小节映射时，先从原谱跨谱表的小节线确认边界，再与拍号和各声部时值交叉核对。符干、局部线段和留白都不自动构成小节线；旧 XML 拆出的格数不能作为原谱小节数。发现拆分错误时，应撤回依赖旧编号的覆盖结论，保留原谱到旧槽位的对应关系，再验证合并没有改变真实起音、持续时间或方向记号的时点。

印刷小节号与播放器内部序号分别记录，尤其注意从 0 开始的弱起或自由段。独立引擎 SVG 的顺序号不一定是产品叠加后的标签；先核对源谱、XML、定位状态与实际界面显示的对应关系，再判断编号偏移，不能为适配内部序号重编号原谱。

低清细节、异常音程或复核意见不一致时，回到高分辨率原谱，按谱号与五线位置重新定标，并由另一位复核者独立确认后锁版。

源符号缺失或互相矛盾时，分开记录可见图形、声部间对齐依据和编辑恢复；不能以凑满拍号代替裁决。确需补点或补符干的可播编辑稿，要保存原读法及恢复理由，并核查受影响音符的起音、延音终点和其他声部是否保持预期。

放大图像不能补回原本不存在的像素。扫描 PDF 的密集符头无法裁决时，先检查页内嵌的原始扫描图是否比整页渲染更清楚，再用同页附近已明确的符头作对照；保留原件、提取链和局部五线定标。不要靠插值后的黑色块面积，推定多出了一个音。

二轮音高复核先暂时脱离底稿：在能清楚辨认五条线的原谱裁图上，逐谱表确定谱号与线位，独立记录音名、时值和声部，再与 XML 比较。尤其检查空心符头、相邻分部和钢琴缩谱；按底稿音名回看低清整页，容易把整段偏一个线位的错误继续当作正确。发现这类系统性误读时，应撤回受影响范围的旧验收，扩大源谱重读范围；XML 到 MIDI 一致不能替代这一步。

源先台账同样可能读错，不能因为先写出就成为标准答案。出现成组高低一音级的差异时，保留原台账，重新从未插值的局部原图列出五条线、加线及符头位置，记录谱号和八度换算，再裁决差异。查看器缩放后的屏幕坐标不能与原图坐标混用；另一份 XML 或从台账生成的 MIDI 一致也不能裁决。另一位复核者的源读与同一作者的逆向自审应分别标注。

调号还要做一次反向例外审计：找出 XML 中所有偏离当前调号的音，逐一定位原谱的临时记号及有效范围；同时从原谱反查临时记号有没有被漏掉。尤其检查键盘缩谱中的自然音假设和跨小节继承，不只检查带 accidental 显示标签的音。PDF 字形清点可以帮助定位，但无法单独证明音名、记号归属或声部正确。

扫描五线倾斜或弯曲时，在音符实际横向位置定标，并用附近加线交叉检查。不能拿左端或上一组音符的纵坐标贯穿整行；密集华彩的末尾尤其容易整体偏一个音级。意见一致也不代替坐标证据，整合后仍按最终文件核对已裁决的音名。

每个反复或跳转标记都需要原谱位置与明确路线。OMR 新增的奏法和表情逐类复核；数量异常、全曲贯穿或彼此矛盾时优先排查。原谱确实存在的记号应保留，不能用“全部删除某类元素”替代复核。合法记号即使音乐含义错误，也可能通过 XML 校验。 重建乐谱或修改音高后，还要对照原谱查看实际升降号；MusicXML 将声音音高与显示记号分开，只有正确的声音音高不保证渲染器已画出必需的临时记号，遗留的还原号也可能让降音显示成自然音。标准记号矛盾可由 CLI 提醒，最终仍按原谱裁决。

歌词核对要落到具体音符。先从源谱独立确定新发音、延音链及换字，再核对每个音节所在音符、连字符和延长线。整段词序或每小节字数一致只能用于筛查；连音线可能跨越不同歌词，不能一律按延音线处理并跳过后续换字。

检查歌词连接时，要跨过中间没有新字的音符，并检查重排后的换行边界；只比较相邻有字音符会漏掉连字符。不同声部接续同一句歌词时，先确定原谱的文字位置和延长线终点，不能让某声部的空白一直继承到另一声部的新词之下。

同一声部中的下一次换字可以为单个长音的延长线提供自然终点，不必为了凑齐同音符上的 start/stop 而漏掉原谱横线或制造新音符。 但下一词之前若有休止，必须回到原谱确认横线是否已在最后一个发声音符处结束；不能把下一词当作默认终点，让延长线穿过休止。源谱支持有限终点时，在现有音符上明确编码边界，并在实际渲染中检查停止位置。先用最小例验证实际解析与绘制；另一 voice/verse 的新字不一定能终止当前线。某个渲染器漏画合法编码时，应记录能力缺口并修复工具，而不是把正确源数据改成方便通过截图的另一种音乐。

## 验证分层，结论限定范围

结构校验、XSD、渲染、播放和原谱核对回答不同问题，应分别记录结果。播放器成功加载不能证明音准和节奏；实际 MIDI 的音高、起点、延音持续时间和播放顺序才有相应证明力。渲染应覆盖全曲及所有声部，重点回看歌词、奏法、表情与结构记号，而非只看改过的几个小节。

定位显示异常时，先读取当前实际载入文件的具体记号和边界，再区分源数据遗漏、解析丢失与绘图策略。记号数量一致不能证明上下位置或线尾正确；不要为了适配显示而改变正确的音乐边界。

表情文字、虚线和渐强渐弱要分别记录原谱图形范围、选择的记谱锚点和实际播放效果。原谱浮动排印或延长音末端没有精确拍点时，明确标出编辑性锚点，不能把纸面横坐标换算成精确演奏时刻。跨系统终点还要核对属于前小节末还是后小节起点：两者可以声音时间相同，却产生不同的换行线尾；保留原谱范围并重新查看完整系统。生成小节内位置时读取目标处的有效 divisions，再用实际出图确认位置，不能沿用首小节的数值。

多声部与和弦还需检查实际画出的音符。重复给每个和弦成员编码连梁，可能通过 XSD 并保持 MIDI 正确，却让渲染器隐藏或折叠符头与连梁。对照源谱查看密集和弦、共同符头、相反符干及跨谱表延音；以最终组合文件的完整图验证，不能沿用组合前组件的显示结论。

离线谱图进入视觉验收前，先证明字体、基准字号与缩放来自实际渲染环境。 截图与绘图脚本也需要验证：样式资源必须使用引擎支持的类型，并检查实际 SVG 的填充和描边有效。音头正常而连线缺失时，先排除验证脚本的样式错误，再判断产品是否丢失记号。SVG 的相对字号不能被截图脚本重复缩小；截图应保留字体与版本证据，并用真实界面的局部交叉检查。若截图链路出错，撤回受影响的排版与遮挡结论，保留原 SVG 后重绘复核；源谱、文件回读和声音证据分别判断是否仍有效。

源 XML、CLI 图和产品图分别检查标题及署名角色。作曲、作词、编曲、版权和编辑说明应按原件保留；播放器内部的通用作者字段可能给编曲者加上“作曲”标签，即使 XML 元数据正确、音符与 MIDI 完全不变，也仍须修复产品显示。用于追踪进展的内部状态文字不应混入原谱方向文字，编辑恢复的说明另留在可追溯记录中。

全曲逐小节定位、短段独奏和整曲连续播放分别记录。定位检查覆盖谱面与游标位置，短段非零 PCM 证明合成有声；这些结果不能证明从头到尾连续播放无停滞、遗漏或错误跳转。连续播放应绑定文件和引擎版本，记录实际经过的小节、结束行为及所用速度；音高与时值仍与独立源台账核对，主观耳听只有实际完成后才计入。

复核必须绑定同一份候选文件。分工时明确各人的声部和检查类别，汇合后检查声部间对齐与全曲行为；合并后的文件再渲染、再播放，旧哈希下的结论只作为历史证据。保留“已检查范围、未检查范围、未解决问题”，不以检查次数或测试数量代替音乐结论。

分工汇合时，还要证明已确认的源谱结论真正进入最终文件。独立源台账之间有冲突，先回到原图裁决并撤回旧结论，再按最终候选逐项核对裁决结果；不得让早期底稿或旧台账覆盖后来的源谱确认。用源台账到最终 XML 的差异清单检查遗漏，不能只确认修改脚本执行过，或只比较 XML 与自身导出的 MIDI。源台账、差异报告和筛选摘要只负责定位；裁决前应查看最终文件的完整小节及上下文，不能把摘要未列出的事件当作遗漏。 从候选 XML 导出的台账只能定位，不能计作独立原谱复核；先看源图记录，再与 XML 比较，才能形成不同来源的校验。

共享符头需要先按符干与延音线恢复每个声部的独立时间线，再检查合成时是否合并同音攻击。两个声部可以在同一符头上同音、同拍、同时值，单看音高集合或最终 MIDI 会漏掉一个声部；反过来，只有一个符干的音也不应复制给另一个声部。分别核对源谱声部归属、最终 XML 声部覆盖和实际播放去重，不能用其中一项替代其余两项。

播放还需区分音符正确与表达实现。文字速度、自由节拍、延长记号等若未被当前引擎执行，应记录实际行为；任何演奏解释都与原谱明确数值分开。只有实际听过才记录耳听通过。共享钢琴符头等多声部写法需要区分谱面事件与实际击键：保留所有源声部，再核对合成前 MIDI 和实际合成结果，不能仅靠音符数量相等判定播放正确。

表达播放按作用区间检查，既看开始，也看停止、重置和声部范围。后续重新写出的相同力度仍是明确指令，应检查它是否结束此前渐强或渐弱的推断；不能只检测力度数值发生变化的地方。以“原谱指令→实际事件→边界后行为”验证，再把修复回用于其他作品。

力度显示另核对明确声明的位置，包括休止符上的声明与重复的同值声明。播放时的继承值不应变成新的印刷记号，源谱记号也不能因该拍没有发声而被丢弃或移到后面的音符。音符力度正确与谱面声明正确需要分别验证。

文字表达先读完整词组，再解释单词。例如 `non dim.` 否定渐弱，`non troppo dim.` 限定程度；识别出 `dim.` 并不证明应执行渐弱。建立源谱表达台账，区分印刷文字、作用声部与引擎实际效果。新旧输出一致只能说明未引入变化，不能排除两版共有的误解；需用源谱明确支持的对照验证其含义，再检查其他作品中的同类表达。

速度要独立核对记谱单位、附点、每分钟拍数和实际生效时点。先换算成四分音符 BPM，再检查引擎导出的全曲 tempo 事件；同一位置的文字/节拍器与 sound 不应互相错误覆盖，小节内 offset 必须按当前 divisions 换算。以附点四分音符 56、二分音符 54 及小节中途变速作为跨作品回归案例，不能只读播放器顶部的速度数字。若引擎只能显示等价四分音符标记，明确区分源 XML 保留情况、显示限制与实际速度正确性。

视觉游标、当前拍事件与声音时钟也要分别核实。谱面横向距离并非等比例时间轴；平滑游标可能朝下一音符插值，经过小节线后的留白。不能仅凭游标越过小节线就认定音乐不同步；先核对引擎设计、下一音符位置及真实事件时序，再判断是否影响排练。调整默认行为前，同时评估停顿、跳动和维护成本。

## 工具改进跟随真实障碍

工具阻挡正确记谱或产生错误显示、播放时，先建立能复现该问题的例子，再修复、补回归、更新用法，并回到真实谱验证。保留原谱合法的部分声部与共享音符；确需接受工具警告时逐项写明依据、绑定输入和输出哈希，警告仍留在报告中。当前 CLI 不支持的操作可使用范围明确、保护未改音乐、可追溯的例外处理。

原生播放器修改进入产品前，另从最终打包制品做干净安装，启动真实准备与渲染 Worker，并核对实际字体和修正症状。开发目录链接、源代码测试或同一份旧包的历史结果，不能证明宿主最终加载了该修改。 发布候选本身也要在该安装包中加载全部声部，完成整曲分页与横向布局；CLI 整谱出图和 MIDI 正确，不能证明产品的多声部音头布局不会中途崩溃。页面表现与部署结果不同时，核对当前标签实际加载的脚本哈希，并在固定新包中独立复现，不能把旧页面和真实引擎缺陷归成一个原因。

工具测试验证工具行为，源谱复核验证音乐内容。工具版本确定后记录提交与测试证据，再应用到后续作品；没有实际需要时无需修改代码。

## 发布后的反馈继续进入闭环

用户反馈先定位产品当前实际文件，再与原谱、复核候选对照。修复应回到成员端验证同一症状；可靠的局部修订可以先更新产品，继续清楚标注剩余范围。将失败原因转成流程判断标准，并检查其他作品是否受到同类问题影响。

本流程的一次具体教训：2026-10-17，《If Music》第一轮发布文件含 39 个假跳音、7 个第一结尾（ending）元素；7 个元素不等于 7 段结尾。结构及播放加载检查允许这些合法 XML 元素，按段落看音区与旋律也未覆盖它们。第二轮校订候选已修正相关记号，但等待钢琴整合、尚未更新产品，使错误继续暴露。由此加入“记号分类复核、从 XML 反查原谱、发布后复现修正项”的要求；第一轮快速覆盖同样执行这一最低检查。


密集歌词在原有系统中被挤压时，先检查和弦是否重复挂了歌词。保留源文字和音乐事件，另出自动重排图（`--breaks auto`，必要时 `--lyric-word-space 2.5`），并保留原件哈希与渲染参数；原有换行仍作另一份参考。重排后应看完整曲目，因为新的换行也可能造成原来没有的文字或符号遮挡。CLI 裁图可读不等于产品显示或自由段播放已通过。
